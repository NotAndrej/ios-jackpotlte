# jackpotlte-gl

The OpenGL ES side of M4 (the GLES route, `docs/jackpotlte-mali.md` §6 and §9).
What lives here so far is one generated file; the `EAGLContext` implementation
that uses it is not written yet.

## `eagl_slots.txt`

The dispatch table that iOS's OpenGL ES is called through. iOS does not call
`gl*` by name: `-[EAGLContext getMacroContextPrivate]` returns a table of
function pointers, and its caller — CoreAnimation's window-server renderer, for
one — calls `entry(table[0], arguments...)`. Entry 0 is the `EAGLContext`; the
rest are the API. The offsets are a property of the build's
`OpenGLES.framework` and nothing in the SDK states them, so they are read off
the framework's own code (see `tools/jackpotlte/eagl-slots.py`).

This copy is the phone's own build: iOS **16.7.16 (20H392)**, iPhone X
(`iPhone10,3`) — the iOS root the port boots, whose cache is in
`/System/Library/Caches/com.apple.dyld/` (hard-linked from the SystemOS
cryptex). 409 entries, 457 names; some entries have two names (an `APPLE`/`EXT`
alias), e.g. `0x2040 glTexStorage2D glTexStorage2DEXT`.

It was generated by reading the cache **in place** out of the 16 GiB HFS+ root
image, because the host had no room to extract it: the cache files are hard
links, their link records break a normal HFS+ walk, and they were found as the
`[HFS+ Private Data]/iNode*` files that begin with the cache magic
(`eagl-slots.py --hfs-image`).

**Cross-check:** the same comparison against the reference's table for iOS 16.5
(20F66, its `userland/src/eagl_slots.txt`) gives 457 names, 409 offsets, no
offset difference for any name and no difference in which names share an entry.
The layout did not change between those two builds. The table here is still the
one generated from this phone's build, not a copy.

What is *not* here: which entries QuartzCore actually calls. The reference marks
them (`*`) by reading them off QuartzCore's renderer; the generator does not
compute that, and the table does not need it — the marks only narrow tracing.

## Regenerating

```
pip install capstone            # and pytsk3 only for --hfs-image
tools/jackpotlte/eagl-slots.py CACHE_DIR         -o userspace/jackpotlte-gl/eagl_slots.txt
tools/jackpotlte/eagl-slots.py --hfs-image IMAGE -o userspace/jackpotlte-gl/eagl_slots.txt
```

`CACHE_DIR` is a directory holding `dyld_shared_cache_arm64` and its `.01`,
`.02`, … subcaches, as an extracted iOS root or restore image has them.

## `gl_slots.h`, `gl_slots.c`

Generated from `eagl_slots.txt` and the Khronos registry by
`tools/jackpotlte/eagl-glue.py`, and checked in (the arm64 build has no Mesa
source at hand to regenerate them):

```
GL_XML=/path/to/mesa-25.0.7/src/mapi/glapi/registry/gl.xml
tools/jackpotlte/eagl-glue.py eagl_slots.txt "$GL_XML" --header > gl_slots.h
tools/jackpotlte/eagl-glue.py eagl_slots.txt "$GL_XML"        > gl_slots.c
```

`gl_slots.h` has the GL types of the ARM64 ABI and `JACKPOTLTE_GL_SLOTS` (1034
entries); `gl_slots.c` has one function per named entry that drops the first
argument (the context) and passes the call on, plus an "unsupported" function
for every entry the build exports no `_gl*` name for (624 of them), so a call to
one is noted instead of crashing. Entry 0 is the context and is the caller's to
set.

The entries do not call the library by name. They ask `jackpotlte_gl_proc` for
it, once. By name would reach the wrong driver: iOS's own `OpenGLES.framework`
is in the shared cache and defines every `gl*` symbol, so a direct call lands on
Apple's, which knows nothing of this context (`jackpotlte_gl.h`).
